# 플랫폼 전환 결정 기록 (2026-10-24)

승인된 계획: 로컬 k3d 플랫폼 전환(GitOps·카나리·섀도우·다중 프로토콜·eBPF·검진센터·보안). 기존 decision-1(EC2 1대 + compose), decision-3(CloudFront 단일 오리진), decision-10(Next static export)을 로컬 플랫폼에서 대체·확장한다. AWS 경로는 AWS 단계 태스크까지 레거시로 유지한다.

## 결정
| 항목 | 결정 | 이유 |
|---|---|---|
| 실행 환경 | 로컬 전용. 8GB M1, UTM의 Rocky Linux 9.8 VM(rocky-dev, 5GB, GenericCloud 20260525 aarch64) 안에 k3s 직접 설치, 컨테이너는 Podman. Docker는 사용하지 않음(2026-10-24 삭제) | 비용 $0. 배포 전에 모두 로컬에서 구성·검증한다 |
| 메모리 운영 | 프로필(core·gitops·protocols·delivery·shadow·ops)로 필요한 것만 켠다. 절차는 스크립트로 강제(k3d와 make test 동시 실행 차단, Docker 메모리·예산 검사) | 8GB에서 전부 동시에 띄울 수 없다. 사람의 기억에 의존하지 않는다 |
| LB·인그레스 | k3s 내장 ServiceLB + Traefik(가중치 라우팅·미러링). 맥 브라우저는 UTM 공유 네트워크(NAT)의 VM IP로 직접 접속하고 맥 /etc/hosts에 이름 1개(예: board.local)를 둔다 — 포트 포워딩 없음(2026-10-29 유저 결정) | k3s 기본 구성이고 카나리·섀도우를 모두 지원한다 |
| 관리형 범위 | 확정(2026-10-29, decision-11): 관리형 미사용 — DB·Kafka·MinIO·GHCR·Prometheus·cert-manager 직접 운영, CloudFront 없음. Cognito·SMS·SSM·Budgets만 유지. AWS 노드는 t4g.large 스팟 1대, LB EC2 없음 | 비용(약 $22~27/월, 밤 정지 시 약 $15)과 학습. 코드는 S3 API·OCI·External Secrets 호환을 유지 |
| 프론트·백엔드 | 같은 저장소, 별도 서비스(Next standalone 서버 + Spring). 한 호스트에서 / 와 /api로 라우팅 | SESSION·XSRF 쿠키 동일 오리진 유지, 둘은 API로만 통신 |
| GitOps·CI/CD | Argo CD core 모드, GitHub Actions → GHCR(커밋 SHA 태그) → 매니페스트 태그 갱신 → Argo 동기화 | 메모리 절약, 표준 GitOps 흐름 |
| 배포 전략 | Argo Rollouts 카나리(Prometheus 분석, 자동 롤백), Traefik GET 미러링 섀도우 + shadow 프로필 쓰기 차단 + 읽기 전용 DB role | GET도 DB에 쓰므로 미러링만으로는 안전하지 않다 |
| 모니터링 | 로컬 Prometheus(+선택 Grafana). CloudWatch는 AWS 단계 | 로컬에서 CloudWatch를 쓸 수 없다 |
| 이벤트 | 트랜잭셔널 outbox + Kafka(KRaft 단일 노드, 작은 힙), inprocess 대체 경로 | 비동기 구조가 없었다. 업계 표준 학습 |
| 프로토콜 | REST + gRPC(4유형) + Connect/gRPC-Web + GraphQL(+구독) + WebSocket/STOMP + SSE + Kafka + Webhook + MQTT + JSON-RPC. 모두 기존 서비스 위의 어댑터 | 비즈니스 로직 중복 없이 프로토콜을 학습 |
| 보안 | 백엔드·프론트 하드닝과 공급망 보안을 앞쪽에 둔다(doc-3). 프로토콜마다 인증·인가·한도·Origin을 AC로 명시. 마지막에 전체 점검 | 새 프로토콜에는 기존 방어가 자동으로 적용되지 않는다 |
| eBPF | C(libbpf·CO-RE, 커널·사용자 공간 모두 C) 에이전트 1개(DaemonSet), 모듈 3종(네트워크 건강, 런타임 보안, 지연 프로파일러) | 하나로 묶어 메모리 절약 |
| 검진센터 | Java Spring Boot 별도 모듈·서비스 + 관리자 화면. 종합 점검, 자동 진단 스냅샷, 인시던트·런북, 장애 주입 연습 | 게시판이 죽어도 살아 있어야 한다. 백엔드와 같은 도구·패턴 재사용, JVM 다이어트로 약 200MB |
| 실배포 대비 | 백업·복구·무중단, SLO·알림·런북, 배포 안전장치, 개인정보·법규. 인증서·DNS·비용·업그레이드는 AWS 단계 | 유저 선택 |

## 변경 이력
- 2026-10-24 개발·배포 OS를 Rocky Linux 9로 통일, 컨테이너 Podman, VM은 UTM(AppleScript는 저장소), Docker 삭제. eBPF는 C, 검진센터는 Spring으로 변경(유저 결정). AWS EC2도 Rocky 9.
- 2026-10-24 OS 버전 확정: Rocky Linux 9.8(10 아님, 유저 결정). AWS EC2도 같은 9.8 arm64.
- 2026-10-29 VM 접근: 포트 포워딩 대신 VM IP + /etc/hosts 이름 1개(유저 결정). 한 호스트에서 / 와 /api 로 라우팅해 같은 오리진 유지. 실제 AWS 배포는 로컬에서 할 수 있는 것을 모두 끝낸 뒤(TASK-52)로 미루고, TASK-18 AC #1(실배포 health 200)은 TASK-52로 옮긴다(유저 결정).
- 2026-10-29 관리형 범위 확정(decision-11): 관리형 미사용, 스팟 1대·LB·CloudFront 없음. 도메인·WAF는 TASK-52에서 결정. Terraform 얼개(TASK-65), Infracost(TASK-66), SonarQube·SonarQube for IDE(TASK-67)를 로컬·CI에 추가(유저 결정).
